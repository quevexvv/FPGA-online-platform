# Регистрация и сессии

Локальная реализация для двух задач: регистрация студента и вход / текущий
пользователь / выход. Подключение PostgreSQL и TPU ID остаётся отдельной работой.

## Локальный запуск без Docker и PostgreSQL

Из корня репозитория:

```bash
cd src/backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
DATABASE_URL=sqlite:///./fpga-local.sqlite3 uvicorn app.main:app --reload
```

Документация API: http://127.0.0.1:8000/docs.

Переменная перед командой имеет приоритет над старым DATABASE_URL в `.env`.
Данные сохраняются в `src/backend/fpga-local.sqlite3`; файл исключён из Git.
При запуске на SQLite Alembic автоматически создаёт/обновляет локальную схему,
включая таблицу сессий из миграции `0002_create_auth_sessions`.
SQLite разрешена только для development/test. Для PostgreSQL автоматического
применения миграций при старте нет; его подключение сегодня не выполнялось.

## Контракт API

| Метод | Путь | Тело / заголовок | Успех |
|---|---|---|---|
| POST | `/auth/register` | `email`, `full_name`, `password` | 201, публичный профиль |
| POST | `/auth/login` | `email`, `password` | 200, `user`, `csrf_token` и cookie |
| GET | `/auth/me` | Cookie `fpga_session` | 200, публичный профиль |
| GET | `/auth/csrf` | Cookie `fpga_session` | 200, CSRF-токен текущей сессии |
| POST | `/auth/logout` | Cookie и `X-CSRF-Token` | 204, сессия удалена |

Регистрация не выполняет автоматический вход. Запрос регистрации:

```json
{
  "email": "student@example.com",
  "full_name": "Иван Михайличенко",
  "password": "My strong password 123"
}
```

Email приводится к нижнему регистру, пробелы по краям email и имени убираются.
Email должен иметь корректный формат и быть уникальным без учёта регистра;
повторная регистрация возвращает 409, включая конкурентные запросы.
Пароль — от 12 до 128 символов; пробелы в нём сохраняются. Имя — 1–200 символов
после удаления пробелов по краям. Ошибки формата возвращают 422 без копирования
введённых значений в ответ. Роль назначает сервер: только `student`.
Передавать `role`, `is_active` и другие дополнительные поля запрещено.

## Поведение сессии

Пароли хранятся как Argon2id-хеши. Cookie содержит случайный токен сессии;
в БД сохраняется только его SHA-256-хеш. Cookie: HttpOnly, SameSite=Lax,
Path=/; в production дополнительно Secure. Срок — 24 часа; параметр
`SESSION_TTL_SECONDS` допускает 60–604800 секунд. При повторном входе старая
сессия текущего браузера отзывается. Сессии других браузеров сохраняются.

Выход удаляет серверную сессию и cookie. Скопированный старый токен после
выхода не работает. Истёкшие сессии отклоняются и очищаются; неактивный
пользователь также не может войти или продолжить использование сессии.
Для неизвестного email, неправильного пароля и неактивного пользователя
возвращается одинаковая ошибка 401. Профиль не содержит password_hash.
Ответы `/auth/*` имеют Cache-Control: no-store.

## Фронтенд

В запросах использовать `credentials: 'include'`. После входа сохранить
`csrf_token` из ответа в sessionStorage и передавать в `X-CSRF-Token` при
выходе. После успешного выхода удалить его. Сессионная cookie недоступна JS.
Если token потерян (например, открыта новая вкладка), получить его через
`GET /auth/csrf`. Токен привязан к сессии и одинаков для её вкладок.
Для будущих маршрутов, которые меняют данные в авторизованной сессии,
использовать зависимость `require_csrf`; для чтения профиля — `get_current_user`.

Запросы регистрации и входа проверяют Origin. Для выхода дополнительно
проверяется CSRF-токен. Разрешённые адреса фронтенда задаёт `CORS_ORIGINS`;
по умолчанию это http://localhost:5173 и http://127.0.0.1:5173.
В локальной разработке открывать API и фронтенд на одном имени хоста
(например, оба через localhost). Cookie SameSite=Lax рассчитана на
размещение фронтенда и API в пределах одного сайта.

В Swagger последовательно выполнить register → login → me → logout.
В logout вставить `csrf_token` из ответа login в поле X-CSRF-Token.
Повторный me должен вернуть 401.

## Проверка

Из `src/backend`:

```bash
python -m pytest -q
ruff check .
```

Тесты авторизации используют отдельные SQLite-файлы во временной папке,
проверяют в том числе конкурентный дубль email, отзыв сессии, CSRF,
неактивного пользователя и сохранение сессии после перезапуска.
Шесть интеграционных тестов PostgreSQL требуют TEST_DATABASE_URL и без неё
пропускаются. В GitHub Actions эта переменная уже задана для отдельной тестовой БД.
