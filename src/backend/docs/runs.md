# Статус проверки своей отправки

`GET /submissions/{submission_id}/run` возвращает последнюю попытку проверки.
Нужна действующая cookie-сессия владельца (`credentials: 'include'`). CSRF для
чтения не нужен. Чужая и отсутствующая отправки дают одинаковый `404`, отсутствие
действующей сессии — `401`, неправильный UUID — `422`. Ответы имеют `no-store`.
Преподаватель не получает доступ к чужим отправкам через этот маршрут.

## Формат для фронтенда

| Поле | Значение |
| --- | --- |
| `submission_id` | UUID отправки |
| `run_id` | UUID последней попытки; `null`, если запуска нет |
| `state` | `not_started`, `queued`, `running`, `finished` |
| `stage` | `null` либо `dispatch`, `validating`, `locking`, `building`, `programming`, `testing`, `finalizing` |
| `mode` | `hardware`, `mock`; `null`, если запуска нет |
| `result_status` | До завершения `null`; затем итог из таблицы ниже |
| `hardware_verified` | Подтверждена аппаратная проверка; у mock всегда `false` |
| `queued_at` | Время создания попытки в бэкенде |
| `started_at`, `updated_at`, `finished_at` | Времена UTC ISO 8601; неизвестные значения `null` |
| `elapsed_seconds` | Секунды с начала исполнения, без ожидания в очереди; до начала `0` |
| `poll_after_seconds` | `3` для активной попытки, иначе `null` |
| `summary` | Итоги всех тестов: `planned`, `executed`, `passed`, `failed`; до завершения `null` |
| `tests` | Результаты только разрешённых открытых векторов; до завершения `[]` |
| `error` | Безопасные `code`, `message` для ошибки исполнителя; иначе `null` |

| Итог (`result_status`) | Отображение |
| --- | --- |
| `passed` | Все тесты пройдены |
| `mismatch` | Есть несовпадения с ожидаемым результатом |
| `build_error` | Ошибка сборки |
| `board_error` | Проверку на плате завершить не удалось |
| `invalid_input` | Исполнитель отклонил входные данные |
| `busy` | Стенд занят, попытка завершена без проверки |
| `internal_error` | Ошибка исполнителя |

Новая отправка создаёт `queued` и новый `run_id` атомарно с исходником.
Старые отправки без попытки возвращают `not_started`; GET не создаёт запуск.
Опрос делать раз в 3 секунды, без параллельных запросов. Прекратить при
`finished`, `not_started`, `401`, `404` и при уходе со страницы. При сетевой ошибке
показать потерю связи и повторить с задержкой, не объявлять работу проверенной.
SSE, ETA, позиция в очереди и маршрут повторного запуска пока отсутствуют.

`starting` исполнителя отображается как `running` со стадией `dispatch`.
Состояние `finished` означает завершение попытки, а не обязательно успех.
`mismatch` может иметь `hardware_verified=true`: плата проверена, ответ неверный.
`passed` в `mock` не подтверждает работу на настоящей плате.

Пример элемента `tests` (иллюстрация формата, не результат реальной проверки):

```json
{
  "vector_index": 1,
  "din": "0x003",
  "steps": 0,
  "dout": "0x00001",
  "expected_dout": "0x00001",
  "mask": "0x3ffff",
  "match": true
}
```

`din` — вход, `expected_dout` — ожидаемый выход, `dout` — полученный.
Битовые значения представлены hex-строками как в контракте стенда: вход 10 бит,
выход/маска 18 бит. `steps` — число тактов, `match` сравнивает выходы по маске.
Служебные пути, логи и исходные сообщения ошибок в браузер не передаются.
`summary` учитывает все тесты, поэтому число элементов `tests` может быть меньше
`summary.executed`. По умолчанию все векторы скрыты, пока преподаватель/команда
не определит разрешённые открытые индексы для набора тестов.

## Приём состояния от исполнителя

Реализованы хранение и проверка снимков по [контракту стенда](../../../docs/contract.md).
Автоматический worker, доставка файлов, вызов диспетчера и опрос стенда ещё
не подключены. Без них новая попытка остаётся `queued`. API не имитирует
успешную проверку и не запускает shell-команды из HTTP-запроса студента.

Для подключения worker должен:

1. Взять сохранённый `run_id` и исходник, выбрать доверенный набор тестов для
   лабораторной. Студент не задаёт режим, команду, пути или список открытых тестов.
2. Установить `configure_public_vectors(db, run_id, indices)` из доверенной
   конфигурации лабораторной до импорта первого статуса; по умолчанию список пуст.
3. Передать задание диспетчеру с этим же `run_id` и зарегистрированным режимом.
4. Получать `status.json`; при `finished` дополнительно читать `result.json`.
5. В транзакции вызывать `record_executor_snapshot(db, run_id, status, result)`
   и делать commit. При ошибке валидации или конфликте версии — rollback,
   заново прочитать БД/файлы и повторить опрос.

Для ручной проверки адаптера из `src/backend` после применения миграций
можно импортировать доверенные файлы исполнителя:

```bash
DATABASE_URL=sqlite:///./fpga-local.sqlite3 python -m app.modules.runs.sync \
  --run-id UUID_ПОПЫТКИ --status /path/to/status.json
```

Для завершённой попытки дополнительно указать `--result /path/to/result.json`.
При первом импорте можно добавить повторяемый аргумент `--public-vector-index 1`
для каждого согласованного открытого индекса. Это настройка оператора, не данные
студента. После начала исполнения список нельзя изменить; повтор того же списка
разрешён. Файлы ограничены 4 МиБ каждый. CLI не создаёт неизвестный запуск.

UUID и режим результата должны совпадать с записью, статус и результат — между
собой. Дубликат не меняет запись, устаревшее обновление отклоняется. Разные стадии
в пределах одной секунды принимаются в прямом порядке, поскольку стенд пишет
время с точностью до секунды. Готовый результат неизменяем. Если `finished`
прочитан без полного результата, прежний статус сохраняется до повторного чтения.
Конкурентные устаревшие записи защищены версией SQLAlchemy.

Для повторной попытки доверенный worker создаёт новую запись через `enqueue`.
Автоматический retry и перепостановка `busy` пока не реализованы. Маршрут возвращает
самую новую попытку по времени создания и UUID; старые результаты остаются в БД.
Публичного HTTP-маршрута записи статуса нет.

## Хранение и проверка

Миграция `0005_add_group_and_runs` добавляет `users.student_group` (API: `group`)
и таблицу `runs`, сохраняя пользователей, сессии, лабораторные и отправки.
На SQLite применяется при старте. Откат до `0004_create_submissions` удалит
группы и историю запусков, но сохранит отправки; это не способ штатного обновления.

`tests/test_run_status_and_group.py` проверяет доступ, состояния, видимость тестов,
согласованность результатов, конкурентные записи, CLI, миграции и поле группы.
Локально: `python -m pytest -q` и `ruff check .`. PostgreSQL-проверки выполняет
существующий CI; устанавливать PostgreSQL или Docker локально не требуется.
