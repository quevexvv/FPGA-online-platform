# Подключение стенда и бронирование

Подготовлено 17.11.2026; дополнено подтверждёнными правилами и сведениями об одной плате.
Документ отделяет подтверждённые требования от вопросов команде.
Это подготовка к реализации, не подтверждение готовности бронирования или подключения.

## Подтверждённые требования

- Студент бронирует конкретную лабораторную на выбранный промежуток времени.
- Начало и конец не привязаны к часовым слотам: допустим пример 13:23–14:05.
- Преподаватель задаёт ограничения длительности. Диапазон 5–60 минут — пример,
  а не утверждённые значения для всех лабораторных.
- Если студент завершил работу раньше, время остаётся занятым до конца брони.
  Завершение работы не является отменой бронирования.
- У следующего студента не появляется право начать раньше окончания предыдущей брони.
- Сейчас используется одна плата, подключённая к ноутбуку интегратора.
  Поддержка 20 плат не входит в текущую реализацию.
- Преподаватель задаёт лимит для конкретной лабораторной.
- Количество отправок в течение брони не ограничено; отдельный кулдаун не добавляется.
- Бронь разрешено отменить до начала. Новое бронирование — после окончания предыдущего.
  Исключение после отмены ещё нужно подтвердить.
- При неявке бронь снимается через 15 минут после начала; следующие брони не сдвигаются.
  Для короткой брони и определения факта появления нужны уточнения ниже.

## Предлагаемые технические правила

Ниже — предложение для согласования до реализации API.

- Бронь хранит владельца, лабораторную, конкретный стенд, начало и конец.
  Брони разных лабораторных конфликтуют, если используют одну плату.
- Интервал задаётся как [начало, конец): соседняя бронь может начинаться ровно
  в момент окончания предыдущей. Пересечение проверяется в одной транзакции,
  включая одновременные запросы двух студентов.
- Бэкенд хранит время в UTC и принимает даты с часовым поясом; интерфейс показывает
  местное время и явную дату. Решение о допустимости запуска принимает сервер.
- Перед передачей каждого задания диспетчеру проверяются владелец брони,
  лабораторная, интервал и доступность ресурса. Проверки кнопки на фронтенде недостаточно.
- Бронь и попытка проверки — разные записи. Создание брони само по себе не запускает HDL.
- Политика лимитов фиксируется в брони, чтобы последующее изменение настройки
  преподавателем не меняло уже подтверждённый интервал без отдельного решения.
- Досрочное завершение не сокращает интервал и не открывает его для новой брони.
  Возможность отмены до начала и её последствия согласуются отдельно.
- Срок сдачи лабораторной и конец брони — разные поля и разные ограничения.

## Подключение диспетчера

Существующий контракт: `docs/contract.md`; инструкция стенда:
`src/fpga/docs/integration-scaffold.md`; импорт результатов: `src/backend/docs/runs.md`.
Адресов и доступов к реальному стенду в этом документе нет.

| Параметр | Что запросить у Вадима |
| --- | --- |
| Размещение | Бэкенд и стенд на одной машине либо разные машины с SSH/SFTP |
| Сеть | Адрес, SSH-порт, необходимость VPN и доступность со стороны сервера бэкенда |
| Учётная запись | Оператор стенда, способ выдачи доступа; секреты передавать отдельно от Git и общего чата |
| Команды | Абсолютный путь к `fpga-dispatch` и необходимая рабочая директория |
| Файлы | Значения `FPGA_JOBS_ROOT`, `FPGA_RUN_CONFIG`, права на загрузку и чтение результатов |
| Сервис | Готовность пользовательского systemd-сервиса и linger для оператора |
| Тестовое задание | Утверждённые условие и шаблон под `counter-v1`, соответствующие ему тесты |
| Открытые тесты | Какие индексы разрешено возвращать студенту |
| Время исполнения | Лимиты сборки/прошивки/тестов; безопасная остановка для границы брони |
| Оборудование | Когда доступны USB-Blaster и UART для аппаратного прогона |
| Очистка | Когда принята реализация cleanup и восстановления из PR №35 |

Предложение: использовать локальные вызовы, если бэкенд размещён рядом со стендом;
иначе SSH/SFTP. Не вводить второй способ подключения до выбора первого командой.
Ни один адрес, путь или способ размещения пока не согласован.

## Порядок обмена после реализации клиента

1. Фоновый обработчик проверяет бронь и резервирует попытку в БД.
2. Формирует пакет с доверенным test_set и фиксирует видимость тестов для попытки.
3. Завершает доставку всех файлов в incoming/<run_id> до вызова submit.
4. Вызывает только `fpga-dispatch submit --run-id <uuid> --mode hardware`.
5. При потере ответа выясняет состояние того же ID; не создаёт новую попытку вслепую.
6. Опрашивает `fpga-dispatch status --run-id <uuid>`, получает status/result и логи.
7. Валидирует и сохраняет результат, затем вызывает cleanup. Ошибка сохранения
   запрещает очистку; недоступность связи не превращается в успешную проверку.

В dev на момент проверки cleanup ещё не реализован; PR №35 открыт.
В обработке busy нельзя создавать новую попытку за пределами действующей брони.
Инфраструктура очереди не заменяет проверку расписания.
