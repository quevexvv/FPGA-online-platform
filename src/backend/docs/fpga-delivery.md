# Доставка пакета на компьютер со стендом

Следующий шаг ONL-92 после [подготовки пакета](fpga-package.md).
Реализована доставка на локальную файловую систему Linux-хоста диспетчера.
Она подходит, если бэкенд и диспетчер работают на одном компьютере.
Фактическое размещение бэкенда ещё нужно подтвердить с интегратором.
Сейчас целевое оборудование — одна плата на ноутбуке Вадима.

## Что делает команда

1. Читает существующую ожидающую попытку и доверенную привязку лабораторной к test_set.
2. Использует ту же блокировку run_id, что и fpga-dispatch.
3. Записывает пакет в приватный временный каталог внутри incoming.
4. После успешной записи обоих файлов переименовывает каталог в incoming/<run_id>.
   Диспетчер не видит частично записанный пакет под именем запуска.
5. Возвращает uploaded либо existing_upload для повторной доставки идентичных файлов.

Команда не вызывает submit, не запускает плату и не изменяет БД.
Статус попытки остаётся queued. Автоматический worker, SSH/SFTP и проверка брони
будут отдельными этапами; HTTP-маршрут доставки студенту не предоставляется.

## Предварительные условия

- Linux-хост диспетчера, один доверенный оператор и обычная локальная файловая система.
  NFS, SMB и другие сетевые файловые системы этим изменением не проверены.
- Абсолютный выделенный каталог FPGA_JOBS_ROOT и его incoming уже существуют.
  Не передавать системный корень / или пути, полученные от студента.
- Каталоги доступны только доверенным процессам оператора. Проверки ссылок не заменяют
  защиту от постороннего процесса, который имеет право менять структуру каталогов.
- incoming и runs находятся на одной файловой системе; runs/.locks при необходимости создаётся.
- Согласована лабораторная и её набор тестов. Пример bindings из fpga-package.md
  необходимо заполнить реальным ID, не привязывать seed-задание И к counter-v1.

## Запуск

Выполнять из src/backend на компьютере, имеющем доступ к локальному каталогу стенда.
Подставить полученные от Вадима пути и существующий UUID попытки:

```bash
DATABASE_URL=sqlite:///./fpga-local.sqlite3 python -m app.integrations.fpga.delivery \
  --run-id UUID_ПОПЫТКИ \
  --bindings /absolute/path/to/bindings.json \
  --jobs-root /absolute/path/to/fpga-jobs \
  --lock-timeout 5
```

Первая строка stdout — JSON с run_id и disposition; следующая напоминает,
что запуск не выполнялся. Это операторская команда, не подтверждение прохождения тестов.
Максимальное ожидание блокировки задаётся в секундах: больше 0, не больше 300.
На macOS/Windows локальная доставка отклоняется; серверная часть работает на Linux.

## Повторы и ошибки

| Ситуация | Поведение |
| --- | --- |
| В incoming уже есть точно такой же пакет | existing_upload, файлы не перезаписываются |
| Исходник/manifest изменён, появились лишние файлы или ссылки | DeliveryConflictError, существующая загрузка сохранена |
| Уже есть runs/<run_id> или незавершённая регистрация .<run_id>.pending | AlreadyRegisteredError; клиент должен выяснить состояние того же ID, не загружать повторно |
| Блокировка занята дольше лимита | TimeoutError; пакет не публикуется |
| Ошибка записи до переименования | Новый неполный каталог удаляется, чужие файлы сохраняются |
| Процесс завершён аварийно | Может остаться .upload-<run_id>-*; он не используется автоматически и требует проверки оператора |

Атомарное переименование гарантирует отсутствие частичного пакета при обычном чтении,
но не является гарантией сохранности при отключении питания. При повторе сначала
проверяется факт регистрации и содержимое существующей загрузки. Если сбой случился
после переименования, повтор вернёт existing_upload вместо перезаписи.
Блокировка защищает доставку и регистрацию диспетчером, но не резервирует строку БД;
такое резервирование должен выполнять будущий worker.

## Проверка

```bash
python -m pytest -q tests/test_fpga_delivery.py
ruff check .
```

Тесты проверяют точное сохранение кода, повторы, конкуренцию, таймаут блокировки,
ошибку записи, ссылки, несовпадающий ID и операторскую команду с временной SQLite.
Отдельный тест передаёт пакет настоящему fpga-dispatch в режиме mock/manual:
первый submit возвращает accepted, повтор — existing. Плата не запускается,
аппаратный результат не подделывается. Linux и jq нужны для проверки диспетчера.

## Дальше

Получить параметры размещения от Вадима. Если бэкенд будет на отдельном компьютере,
реализовать SSH/SFTP с проверкой ключа хоста и согласованными правами.
Затем добавить вызовы submit/status, получение результата и worker с проверкой брони.
Настоящий аппаратный прогон проводится отдельно с интегратором.
