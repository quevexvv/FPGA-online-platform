# Независимое наблюдение через JTAG на C5G

Доверенный проект `jtag_probe` проверяет In-System Sources and Probes
через `ALTSOURCE_PROBE` и `quartus_stp`. Он использует разъём USB-Blaster,
50 МГц и LEDG0. Контрольный сигнал проходит через регистр LEDG0, а
двухбитный пробник возвращает пару `{~led, led}`. UART остаётся свободным.

## Запуск

На стенде с Quartus Prime Lite 23.1 и доступным USB-Blaster выполните из
корня репозитория. Имя кабеля и индекс устройства возьмите из `jtagconfig`.

```bash
make -C src/fpga build-jtag-probe
bash src/fpga/scripts/jtag-observe.sh program 'USB-Blaster [3-1]' 1
bash src/fpga/scripts/jtag-observe.sh probe 'USB-Blaster [3-1]' 1
```

`program` загружает в SRAM только `build/jtag-probe/jtag_probe.sof`.
Повторная загрузка заменяет конфигурацию платы. Запускайте команды
от той же учётной записи, что и аппаратные задания. Обе команды используют
блокировку стенда диспетчера. Код 75 означает занятую блокировку. Через
30 секунд команда останавливается с кодом 124 (137 при принудительной
остановке). Tcl открывает и закрывает JTAG-сеанс в каждом вызове, в том
числе при ошибке чтения. Если между командами обычное задание заменит
прошивку, проверка ожидаемого JTAG-узла сообщит об ошибке.

## Результат эксперимента

Quartus Prime Lite 23.1std.0 собрал проект для C5G. Две последовательные
сессии через `quartus_stp` записали `0 → 1 → 0` и прочитали
`10 → 01 → 10` с зарегистрированного выхода. После закрытия сеанса
подтверждена повторная загрузка. При занятой блокировке наблюдатель вернул
код 75. После физического отключения кабеля наблюдатель вернул код 1
и сообщение Quartus об отсутствии оборудования.

Этот канал подходит для чтения доверенной телеметрии во время работы DUT.
Скорость ограничена JTAG и отдельными транзакциями хоста. При зависании
`jtagconfig` после перестановки кабеля в эксперименте помог перезапуск
пользовательского `jtagd` без изменения его конфигурации. После повторного
подключения и перезапуска службы прошли чтение пробника и загрузка новой
прошивки.

Команды обмена описаны в [руководстве Intel по Sources and Probes](https://www.intel.com/content/www/us/en/docs/programmable/683819/25-1/tcl-interface-for-the-in-system-sources.html).

## Согласованный снимок

После загрузки проекта вызовите:

```bash
bash src/fpga/scripts/jtag-observe.sh snapshot 'USB-Blaster [3-1]' 1
```

При успехе stdout содержит один JSON, а сообщения Quartus идут в stderr.
Пример для состояния `0x002a`:

```json
{"schema_version":1,"state":42,"hex2":119,"hex3":91}
```

`state` — 16-битное состояние свободно работающего счётчика. `hex3` и
`hex2` — маски сегментов старшей и младшей тетрады его младшего байта.
Биты от 0 до 6 соответствуют сегментам `a`–`g`; единица означает
«зажжён». Проект формирует маски внутри ПЛИС и не выводит их на физические
контакты HEX2/HEX3. Это отдельный формат телеметрии эксперимента.

Однобитный запрос проходит синхронизатор IP на 50 МГц. По смене запроса
логика записывает весь снимок за один фронт и через такт меняет
подтверждение. Данные остаются стабильными до следующего запроса.
Клиент сначала ждёт подтверждения для текущего значения запроса
(в том числе после прерванного сеанса), затем меняет его и перечитывает
подтверждённый снимок. Неверный кадр, изменение снимка после подтверждения
или таймаут дают ошибку команды.

`make -C src/fpga test-jtag-snapshot` проверяет захват на ожидаемом
фронте, подтверждение и удержание данных в симуляции.
`tclsh src/fpga/tests/jtag-observe.tcl` проверяет декодирование, таймаут,
неустойчивый кадр и закрытие сеанса с заглушками JTAG.

На C5G проверены 24 снимка из отдельных сеансов. Все 24 состояния
различались, обе маски в каждом кадре совпали с декодированием его
состояния. TimeQuest обнаружил две цепочки синхронизации; минимальный
slack в отчёте составил 0,134 нс при TNS=0. Зарезервированные внешние
сигналы JTAG TDI, TMS и TDO указаны в отчёте как порты без задержек ввода
или вывода.
