# Контракт бэкенда и стенда ПЛИС

Бэкенд отвечает за пользователей, лабораторные, очередь и постоянную историю.
Стенд собирает HDL, прошивает C5G, выполняет доверенные тесты и возвращает
результат. Здесь описано согласованное поведение для реализации. Полный
исполнитель пока не готов; доступные проверки перечислены в
[инструкции FPGA-части](../src/fpga/docs/integration-scaffold.md).

## Размещение и файлы

Quartus, `fpga-dispatch` и внутренний `fpga-run` работают на машине с платой.
Бэкенд вызывает только `fpga-dispatch`. На общем хосте файлы записываются
и команды вызываются локально; на разных — используются SFTP и SSH.
Смысл операций одинаков. Размещение и схема сети пока не выбраны.

Корень данных задаётся при развёртывании. Внутри него:

```text
incoming/<run_id>/       загрузка до submit
runs/<run_id>/input/     опубликованные исходники и manifest.json
runs/<run_id>/output/    status.json, result.json, logs/
runs/<run_id>/work/      промежуточные файлы
runs/<run_id>/control/   регистрация, запуск, отметка cleaned
```

Бэкенд создаёт run_id — UUID в нижнем регистре. Один ID обозначает одно
выполнение. Новая намеренная попытка получает новый ID. Все файлы должны
быть загружены в incoming до submit; после публикации input неизменен.

## Входной манифест и HDL

Пример [manifest.json](../src/fpga/examples/manifest.json):

```json
{
  "schema_version": 1,
  "run_id": "7dd3f420-5916-4d71-908e-b7885c071853",
  "top": "student_top",
  "kind": "sequential",
  "sources": ["src/student_top.v"],
  "test_set": "counter-v1"
}
```

Все поля обязательны. Версия — 1; ID совпадает с каталогом и аргументом
команды; top=student_top; kind — combinational или sequential.
Бэкенд формирует sources и выбирает установленный на стенде доверенный
набор test_set. Эталоны не берутся из студенческих файлов.

Пути исходников относительны input. Абсолютные пути, выход через `..`
и симлинки за пределы задания запрещены. JSON разбирается через jq,
его содержимое не исполняется. Аргументы команд передаются отдельно,
без подстановки студенческих данных в shell.

Студент передаёт только HDL: без команд, QSF/SDC/Tcl, пинов, пути UART,
лимитов и готовых `.sof`. Сборка использует доверенные шаблоны. Секреты
окружения не передаются в сборку и задания. Повседневные процессы работают
без root; udev настраивается администратором. Это не заменяет отдельную
проверку изоляции недоверенного HDL.

Предварительный интерфейс: `student_top(clk, reset, din[9:0], dout[17:0])`.
Reset синхронный, активный при 1; рабочий шаг — положительный фронт clk.
Reset-такты не входят в steps, входы удерживаются во время пачки.
Комбинационная схема не использует clk/reset: steps=0, чтение после
установления выходов. Выход за разрядность запрещён. Интерфейс может
измениться до реализации обёртки; UART студента, SRAM и многочастотные
проекты в него не входят. [Служебный UART-протокол](../src/fpga/docs/uart-protocol.md)
описывает связь компьютера с обёрткой, а не новый API для бэкенда.

## Submit и запуск

```sh
fpga-dispatch submit --run-id <uuid> --mode hardware
```

При удалённом вызове перед той же командой добавляется SSH. Диспетчер
сериализует операции по ID, публикует input, создаёт контрольную запись
и status.json со state=starting, stage=dispatch **до ответа accepted**.
Ответ содержит schema_version, run_id и disposition=accepted. Это регистрация,
а не подтверждение свободного стенда, корректности HDL или успешного теста.

Затем запускается независимый пользовательский systemd-сервис с linger
и Restart=no, внутри которого работает блокирующий fpga-run. Обрыв SSH
или завершение процесса бэкенда не останавливают исполнение.

Повтор зарегистрированного ID возвращает disposition=existing без нового
исполнения. Менять режим и опубликованные файлы нельзя: нужен новый ID.
Незарегистрируемый запрос завершается ошибкой команды без accepted;
ошибки зарегистрированного задания оформляются результатом.

## Hardware и mock

Бэкенд выбирает hardware для сдачи, mock — для демонстрации готового примера.
Студент не выбирает mock как способ проверки собственного решения.
Mock не собирает пользовательский HDL, не прошивает плату и не открывает
UART. Он возвращает заранее подготовленные данные. Симуляция произвольного
HDL — отдельная будущая функция. Код эталона не передаётся в браузер.

Автоматического переключения hardware в mock нет. Режим сохраняется
в контрольной записи, статусе, результате и передаётся сайту.
Демонстрация явно помечается и не засчитывается как аппаратная сдача.

## Status и публикация результата

```sh
fpga-dispatch status --run-id <uuid>
```

Диспетчер проверяет процесс, оформляет обнаруженные аварии и возвращает
актуальный status.json. Все поля обязательны:

| Поля | Значение |
|---|---|
| schema_version, run_id, mode | 1, UUID, hardware или mock |
| state | starting, running, finished |
| stage | dispatch, validating, locking, building, programming, testing, finalizing |
| started_at | UTC; null до начала исполнения |
| updated_at | UTC последнего обновления |
| finished_at, result_status | null до завершения, затем время и итог |

Обычный путь — starting → running → finished. Ошибка до старта может
завершить задание прямо из starting. Очередь — состояние бэкенда, не стенда.
Mock не выполняет аппаратные стадии. Сайт показывает стадию и прошедшее
время; процент и ETA не обещаются. Долгая стадия не доказывает зависание.

JSON публикуется через временный файл и атомарное переименование на том же
файловом разделе. **Сначала result.json, затем status.json со state=finished.**
Бэкенд читает результат и перечисленные в нём логи после finished.

## Поля результата

Обязательны schema_version, run_id, mode, status, hardware_verified,
started_at, finished_at, summary, observations, error, logs.
Примеры: [hardware](../src/fpga/examples/result.json),
[mock](../src/fpga/examples/result-mock.json). Их данные вымышлены.

| Итог | Значение |
|---|---|
| passed | Все проверки выполнены и совпали |
| mismatch | Все проверки выполнены, есть несовпадения |
| build_error | Ошибка или таймаут сборки |
| board_error | Ошибка или таймаут прошивки/обмена |
| invalid_input | Нарушен входной контракт |
| busy | Стенд занят, сборка и аппаратная работа не начались |
| internal_error | Сбой исполнителя или инфраструктуры |

Summary содержит planned, executed, passed, failed. Каждое наблюдение —
vector_index, din, steps, dout, expected_dout, mask, match.
Сравнение: `(dout & mask) == (expected_dout & mask)`.
Error — null или объект stage, code, message; logs — относительные пути
внутри output. Ранняя ошибка допускает пустые observations/logs,
не начавшееся выполнение — started_at=null.

Hardware_verified=true означает прошивку и полный набор аппаратных
наблюдений в данном запуске. Допускается при mismatch: реальные измерения
не гарантируют правильность решения и не являются оптической проверкой LED.
При mock и неполной проверке поле всегда false. Обрыв обмена после части
векторов даёт board_error с сохранением наблюдений. Finished и код завершения
команды сами по себе не означают успешную сдачу.

Полный результат хранит бэкенд. Студенту показываются только разрешённые
векторы, логи и агрегированные итоги скрытых проверок. Разметка скрытых
векторов и фильтрация пока не определены контрактом; весь отчёт нельзя
безусловно пересылать в браузер.

## Очередь, повторы и аварии

- Исполнитель берёт общую блокировку без ожидания. Занятость даёт терминальный
  result.status=busy, затем finished. **Busy не является disposition submit.**
  Бэкенд оставляет отправку в очереди и позже создаёт новый run_id для её
  выполнения. Это не новая пользовательская отправка.
- При таймауте завершается всё дерево процессов этапа, сохраняются доступные
  логи. Блокировка освобождается после остановки дочерних процессов.
  Таймаут запроса сайта не останавливает исполнение.
- Потерянный ответ submit проверяется через status того же ID; повторный
  submit не создаёт второе выполнение. После обрыва SSH опрашивается тот же ID.
- Сбой между регистрацией и стартом, исчезнувший процесс без результата
  и незавершённое задание после reboot оформляются как internal_error.
  Для reboot причина — interrupted/host_restarted. Автоматического перезапуска нет.
- Отсутствие result.json при starting/running нормально. При finished без
  результата бэкенд повторно вызывает status и не выставляет успешный итог.
  Пока хост недоступен, показывается потеря связи; наблюдения не выдумываются.

## История и cleanup

Бэкенд сохраняет результат, нужные логи и исходники по своей политике.
Исполнитель может удалить собственный work после сохранения нужных логов.
Input/output остаются до явного вызова:

```sh
fpga-dispatch cleanup --run-id <uuid>
```

Очищать можно только finished, включая неуспешные итоги. Удаляются input,
output и оставшийся work этого запуска. Активное задание не удаляется.
В control до конца пилота остаётся минимальная отметка run_id + cleaned
без исходников и результата, чтобы поздний submit не исполнил ID повторно.
Повторный cleanup безопасен и не затрагивает другие каталоги.

Незавершённую загрузку в incoming бэкенд удаляет при отмене. Опубликованные
runs очищаются только через диспетчер. Нехватка диска даёт явную
инфраструктурную ошибку; незабранные результаты автоматически не удаляются.

## Открытые решения

Размещение и сеть, числовые лимиты времени/ресурсов/шагов, конкретные
лабораторные и наборы тестов, правила скрытых проверок. На стенде проверены
LED и автономный генератор тактов; полный путь через UART ещё не реализован.
Формат файлов и готовность реализации — разные вещи.
